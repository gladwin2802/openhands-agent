# Databricks Lakeflow & Asset Bundles Knowledge Base

This document provides syntax and configuration details for implementing Databricks Asset Bundles (DABs), Lakeflow pipelines (DLT), and Workflow Jobs with file arrival triggers.

---

## 1. Databricks Asset Bundles (DABs) Configuration (`databricks.yml`)

### Core Structure
```yaml
bundle:
  name: demo
  uuid: f3729d75-7e1d-44c6-977f-cbd544c5c66e

include:
  - resources/*.yml
  - resources/*/*.yml
  - resources/*/*/*.yml

variables:
  catalog:
    description: The catalog to use
    default: ${bundle.target}
  schema:
    description: The schema to use
    default: ${bundle.target}
  pipeline_schema:
    description: The schema for the source volume
    default: landing
  volume:
    description: The volume for source files
    default: data
  target_schema:
    description: The target schema for the pipeline layer
    default: silver
  bronze_target_schema:
    description: The target schema for bronze layer
    default: bronze
  silver_target_schema:
    description: The target schema for silver layer
    default: silver

targets:
  dev:
    mode: production
    default: true
    workspace:
      host: https://dbc-94029e02-4197.cloud.databricks.com
  testing:
    mode: development 
    presets:
      name_prefix: "[${bundle.target} ${workspace.current_user.short_name}] "
  prod:
    mode: production
    presets:
      name_prefix: "[${bundle.target} ${workspace.current_user.short_name}] "
    workspace:
      host: https://dbc-94029e02-4197.cloud.databricks.com
      root_path: /Workspace/Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.target}
    permissions:
      - user_name: ${workspace.current_user.userName}
        level: CAN_MANAGE
```

### Resource Definitions
Resources are typically defined in separate YAML files under `resources/`.
- **Pipelines**: Defined under `resources.pipelines`.
- **Jobs**: Defined under `resources.jobs`.

#### Pipeline Resource Definition Example (YAML)
```yaml
resources:
  pipelines:
    my_pipeline:
      name: my_pipeline
      target: my_target
      catalog: ${var.catalog}
      serverless: true
      libraries:
        - file:
            path: ../../../src/my_entity/my_bronze/transformations/landing.py
        - file:
            path: ../../../src/my_entity/my_bronze/transformations/bronze.py
      configuration:
        catalog: ${var.catalog}
        pipeline_schema: ${var.pipeline_schema}
        volume: ${var.volume}
        target_schema: my_target
```
*Note*: Always specify raw Python transformation scripts (`.py` files) using the `- file:` parameter. Use `- notebook:` only for Jupyter Notebooks (`.ipynb`) or files containing `# Databricks notebook source` headers.

## 2. Lakeflow Declarative Pipelines (SDP) Syntax (Python)

### Basic Streaming Table and Materialized View
```python
from pyspark import pipelines as dp
from pyspark.sql.functions import col, trim

# Create a streaming table and define its loading flow
dp.create_streaming_table("my_streaming_table")

@dp.append_flow(target="my_streaming_table")
def my_streaming_table_flow():
    return spark.readStream.format("cloudFiles").option("cloudFiles.format", "json").load(path)

# Create a materialized view reading from the streaming table
catalog_config = spark.conf.get("catalog")
schema_config = spark.conf.get("target_schema")

@dp.materialized_view(
    name=f"{catalog_config}.{schema_config}.my_mv",
    comment="Description of the materialized view"
)
def my_mv_definition():
    return spark.read.table("my_streaming_table").filter(col("active") == True)
```
*Note*: Always use `spark.read.table("dataset_name")` in Python to read a dataset created in the same pipeline/package.

### Expectations (Data Quality)
In Lakeflow, expectations function as decorators stacked directly on the `@dp.materialized_view` or `@dp.append_flow` function definitions.
```python
@dp.expect("valid_id", "id IS NOT NULL")
@dp.expect_or_drop("valid_date", "date > '2020-01-01'")
@dp.expect_or_fail("critical_field", "field IS NOT NULL")
@dp.materialized_view(name=f"{catalog_config}.{schema_config}.my_mv")
def my_mv():
    return spark.read.table(...)
```

### Configuration Access
Fetch variables dynamically from `spark.conf` using the active `SparkSession`. Ensure `SparkSession` is imported correctly from `pyspark.sql` (NOT `pyspark.sql.functions`). Use the correct keys matching the pipeline configuration block:
```python
from pyspark.sql import SparkSession

spark = SparkSession.getActiveSession()
catalog = spark.conf.get("catalog")
pipeline_schema = spark.conf.get("pipeline_schema")
volume = spark.conf.get("volume")
target_schema = spark.conf.get("target_schema")
```

### Primary Key Constraints (Python)
In Lakeflow Declarative Pipelines, primary key constraints are informational and unenforced by default. 
To specify a primary key constraint, you MUST declare it within the `@dp.materialized_view` decorator by passing a DDL-formatted schema string. Do NOT run `spark.sql("ALTER TABLE ...")` at the module level in your Python files.

Example:
```python
@dp.materialized_view(
    schema="""
        distributor_id INT NOT NULL PRIMARY KEY,
        distributor_name STRING,
        phone_number STRING,
        street_address STRING,
        postal_code STRING,
        city STRING,
        state STRING,
        country STRING
    """,
    name=f"{catalog_config}.{schema_config}.distributor_mv",
    comment="Silver materialized view with primary key constraint"
)
def distributor_mv():
    df = spark.read.table(...)
    # Apply transformations...
    return df
```

## 3. Change Data Capture (CDC) & SCD Type 2

### Using `create_auto_cdc_flow` (Lakeflow SDP)
In Lakeflow, we do not use legacy `dlt.apply_changes`. Instead, we create a target streaming table using `dp.create_streaming_table` and then define the CDC flow at module level using `dp.create_auto_cdc_flow`:

```python
from pyspark import pipelines as dp
from pyspark.sql.functions import col, expr

dp.create_streaming_table("consumer_cdc_stream")
dp.create_auto_cdc_flow(
  source = "consumer_raw_stream",
  target = "consumer_cdc_stream",
  name = "cdc_consumer_flow",
  keys = ["consumer_id"],
  sequence_by = col("ingestion_time"),
  apply_as_deletes = expr("operation = 'delete'"),
  stored_as_scd_type = "2" # Specifies SCD Type 2
)
```
*CRITICAL*: `dp.create_auto_cdc_flow` is executed at the module level (outside of any decorated function) and does not return a DataFrame.

## 4. Workflow Jobs & File Arrival Triggers

### Job Definition (YAML)
```yaml
resources:
  jobs:
    my_job:
      name: my_job_name
      trigger:
        pause_status: UNPAUSED
        file_arrival:
          url: /Volumes/catalog/schema/volume/path/
      tasks:
        - task_key: bronze_task
          pipeline_task:
            pipeline_id: ${resources.pipelines.bronze_pipeline.id}
        - task_key: silver_task
          depends_on:
            - task_key: bronze_task
          pipeline_task:
            pipeline_id: ${resources.pipelines.silver_pipeline.id}
      queue:
        enabled: true
```

### Dynamic Value References
- `{{job.trigger.file_arrival.url}}`: The path that triggered the job.

### Resource Path Flattening Rule
> [!IMPORTANT]
> **Reference Flat Keys, Not Folder Structure:**
> When Databricks Asset Bundles compile, all YAML resource files under the `resources/` folder are merged into a single flat namespace. Physical folder structure (e.g. `resources/pipelines/consumer/consumer_bronze_pipeline.yml`) **does not** create a sub-key namespace in the resource map.
> * **Incorrect:** `pipeline_id: ${resources.pipelines.consumer.consumer_bronze_pipeline.id}`
> * **Correct:** `pipeline_id: ${resources.pipelines.consumer_bronze_pipeline.id}`

## 5. Materialized Views (SQL & Serverless)

### SQL Syntax
```sql
CREATE OR REPLACE MATERIALIZED VIEW my_mv
SCHEDULE CRON '0 0 * * * ?' AT TIME ZONE 'UTC'
AS SELECT ... FROM ...;

-- Manual Refresh
REFRESH MATERIALIZED VIEW my_mv;
REFRESH MATERIALIZED VIEW my_mv ASYNC;
```

### Refresh Policies
- `TRIGGER ON UPDATE`: Refreshes automatically when source data changes.
- `SCHEDULE EVERY 1 DAY`: Periodic refresh.

## 6. Rules for Adding a New Data File / Entity to the Project
When adding a new source data file or entity to the project (e.g. `product`, `inventory`), the following files must be updated to keep orchestration in sync:

1. **New Entity Metadata (`instructions/metadata/metadata_<entity_name>.json`):** 
   Create the metadata configuration specifying schema, trigger, CDC rules, and expectations.

2. **Metadata Files (`instructions/metadata/project_metadata.json` & `<target_project>/<project_name>_metadata.json`):**
   - **Global Metadata (`instructions/metadata/project_metadata.json`):** This is a single-run registry. Overwrite this file on every run to only contain the active project name, global config, and the single active entity details (under `bootstrap.entities` and `bootstrap.dependency_graph`).
   - **Project-Specific Metadata (`<target_project>/<project_name>_metadata.json`):** This is a cumulative registry for that project. Update/append the entity details to the `bootstrap.entities` array and its corresponding orchestration task to the `bootstrap.dependency_graph` (preserving all existing entities and tasks in the sequence).

3. **Setup Notebook (`demo/src/bootstrap/setup.ipynb`):**
   - Append the new entity and its target volume directory path to the `input_file_paths` Python dictionary so it is automatically created at startup.

4. **Bootstrap Workflow Job (`demo/resources/jobs/bootstrap_job.yml`):**
   - Add the new task to run the entity's workflow job (using the `run_job_task` type) and specify its execution dependencies (using `depends_on`).

### 2. Base Bootstrap Job Template (`bootstrap_job.yml` - YAML Format)
Create this file at `resources/jobs/bootstrap_job.yml` with the correct task triggering syntax. Note that task dependencies MUST be specified as a list of maps using `task_key`, and the task type for triggering another job is `run_job_task` with `job_id`:
```yaml
resources:
  jobs:
    bootstrap_workflow:
      name: bootstrap_workflow
      tasks:
        - task_key: setup
          notebook_task:
            notebook_path: ../../src/bootstrap/setup.ipynb
            base_parameters:
              catalog: ${var.catalog}
              landing_schema: ${var.pipeline_schema}
              volume: ${var.volume}
              bronze_schema: ${var.bronze_target_schema}
              silver_schema: ${var.silver_target_schema}
            source: WORKSPACE
        # Example of how subsequent entity jobs are sequentially triggered:
        - task_key: run_consumer_job
          depends_on:
            - task_key: setup
          run_job_task:
            job_id: ${resources.jobs.consumer_workflow.id}
      queue:
        enabled: true
```

## 8. Windows Environment (PowerShell) Guidelines
- The execution environment is Windows PowerShell 5.1.
- **Do NOT** use bash statement separators like `&&` or `||` in terminal commands. Doing so causes PS parser errors.
- Always use `;` as a statement separator, or execute commands in separate, sequential runs.
- **Do NOT** use multi-line shell commands (`Set-Content`, `Out-File`, `echo`, `cat`) to create or write file contents in the terminal tool, as interactive PowerShell parses newlines inside quotes poorly and will freeze or hang. Always use the dedicated `FileEditor` tool for file modifications.

## 9. Verification & Logical Correctness Checklist
Before completing any task, the model must audit all configurations and code files for the following logical errors and correct them immediately:

1. **Bundle Variables Match Reference**: Ensure every configuration variable used in the resources (e.g., `${var.pipeline_schema}`, `${var.volume}`, `${var.bronze_target_schema}`) is declared under the `variables` section in `databricks.yml`. Additionally, any variable that is overridden or assigned a value under `targets.<target>.variables` (such as `schema: dev`) must also be explicitly declared in the top-level `variables` section of `databricks.yml`. If they are not declared, deployment/validation will fail with: `variable <name> is not defined but is assigned a value`.
2. **Inclusion Pattern Resolution**: Ensure `databricks.yml` inclusion patterns recursively search folder paths. Always define the explicit list:
   ```yaml
   include:
     - resources/*.yml
     - resources/*/*.yml
     - resources/*/*/*.yml
   ```
3. **Dynamic vs Hardcoded Schema Configurations**:
   - Verify if configurations like `target_schema` should be dynamic variables (`${var.silver_target_schema}`) or hardcoded values.
   - Validate that schema resolution in transformation scripts (e.g. `silver.py`) correctly replacement-maps to the parent layer schema. For example, if target_schema is set to `silver`, then `.replace("silver", "bronze")` successfully evaluates to `bronze`. If target_schema is set to `distributor_silver`, then `.replace("_silver", "_bronze")` successfully evaluates to `distributor_bronze`.
4. **No Module-Level SQL Execution**: Ensure no Python transformation scripts execute `spark.sql("ALTER TABLE ...")` at the module level.
5. **Dependency Mapping**: Validate that job configuration dependencies (e.g. `depends_on` tasks) match the orchestration sequence in the metadata files.
6. **Logical Resource References**: Ensure all referenced pipelines and jobs within the resource configurations (e.g. `pipeline_id: ${resources.pipelines.<name>.id}`) use the flat resource key (like `consumer_bronze_pipeline`) rather than physical directory paths (like `consumer.consumer_bronze_pipeline`).
7. **Dynamic Parent Table Schema Reference**: When query joining parent tables for referential expectations, do NOT hardcode schema names like `consumer_bronze` or `consumer_order_bronze`. Always dynamically query from `f"{catalog}.{bronze_schema}.{ref_entity}_mv"` where `bronze_schema` is resolved from `target_schema` by replacing `_silver` with `_bronze`.
8. **Lakeflow Schema DDL Projection to Prevent Schema Pollution**: When joining a parent table to evaluate expectations (which adds columns like `parent_consumer_id`), you must declare an explicit DDL schema string inside the `@dp.materialized_view(schema="...")` decorator parameter listing only target columns. Lakeflow will automatically project the returned DataFrame to match the DDL schema, dropping any extra helper/validation columns from the final table output.
9. **Spark SQL Imports Verification**: Ensure that all PySpark functions used in transformation scripts (such as `col`, `trim`, `to_date`, `when`, `current_timestamp`) are explicitly imported from `pyspark.sql.functions` to prevent NameErrors at runtime.
10. **Jupyter Notebook JSON Escaping**: When writing or generating `.ipynb` files, ensure string quote escaping uses standard single-escaped `\"` instead of double-escaped `\\\"` in SQL/Python statements.
11. **Production Mode for Multi-Schema Target Deployments**: For target environments (such as `dev`) where Lakeflow pipelines publish to separate, distinct schemas (e.g. `dev_bronze` and `dev_silver`) and reference tables across them, ensure that `mode: production` is used instead of `mode: development`. In development mode, the CLI automatically overrides all pipeline target databases to a single developer-specific schema (like `dev`), which blocks cross-pipeline compilation and causes naming collisions when tables share the same base name across layers.
